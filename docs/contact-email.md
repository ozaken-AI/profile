# お問い合わせフォームとメールの運用

実装確認：2026-09-11。`src/pages/contact.astro` → `POST /api/contact` → `functions/api/contact.js` → Resend → 受信先、という流れ。旧文書には2026年8月に設定済みという記録があるが、それだけで現在の配送成功を保証しない。

## 設定

Cloudflare Pagesの `profile`、対象のProduction / Previewを確認して設定する。

| 名前 | 用途・コードの既定値 |
|---|---|
| Secret `RESEND_API_KEY` | Resendへの送信用キー |
| `CONTACT_TO` | 受信先。未指定なら `kensuke.ozawa@aicx.jp` |
| `CONTACT_FROM` | 差出人。未指定なら `ozaken.ai <onboarding@resend.dev>` |

Resend側で対象の差出人・ドメイン・宛先が使える状態か確認する。独自ドメインを使う場合は、Resendが示す認証用DNSと認証状態を確認してから `CONTACT_FROM` を変更する。試用時の送信制限や契約条件は、実際のアカウント設定を確認する。

キーはSecretsの管理経路から登録し、会話・Git・公開ログに載せない。環境設定後は、その設定を利用するデプロイを反映・確認する。既存の受信先を変更する場合は `SITE.email`、フォームの直接メール・メーラーへの切替先、プライバシーの連絡先も照合する。

## 応答と画面の意味

| 状態 | 関数の応答 | 利用者側の意味 |
|---|---|---|
| JSON形式不正、名前・メール・本文が不足 | 400、`ok: false` | 入力を修正。メールは送らない |
| ハニーポット `website` が埋まる | 200、`ok: true` | bot対策で見かけの成功。メールは送らない |
| `elapsed` が有効な0〜2999ms | 429、`ok: false` | 3秒ほど待って再送。入力は保持 |
| 入力が正しくキーが未設定 | 200、`ok: false, configured: false` | 入力を保持し、利用者が選べるメーラーリンクを表示。自動配送ではない |
| Resendが受け付けた | 200、`ok: true` | 画面に成功表示、入力をリセット |
| Resendがエラーを返した | 502、`ok: false` | 失敗表示、入力を保持 |
| 通信失敗 | フロント側の例外処理 | 失敗表示、入力を保持 |
| GET | 405 | フォームの送信APIはPOSTを使う |

成功判定はHTTPだけでなくレスポンスの `ok` も必要。Resendの受付成功と、最終的に受信箱へ届いたことは別の確認。失敗時に入力を消したり、「送信済み」と表示したりしない。

問い合わせ種別の事前選択はURLの `kind` を `src/lib/contact.js` の許可リスト（`other` / `keynote` / `training` / `partner` / `advisory` / `writing` / `media`）から日本語ラベルへ変換する。任意のURL文字列を選択肢へ追加しない。

## 配送内容

件名は `【ozaken.ai】依頼の種類／名前`。返信先はフォーム入力のメールアドレス。本文には名前・会社・メール・電話・依頼種別・テーマ、依頼種別に応じた時期・対象／関与範囲・相談内容と、送信元IP・UTCの受信日時が入る。実際の問い合わせ内容を公開のPRや障害記録へ貼らない。

## 検証

コード変更時はリポジトリのルートで `npm test`。8件のテストが、3秒未満の送信と再送、配信サービスの失敗、入力不正、キー未設定、最大長、種別・テーマを検証する。外部通信は模擬され、実メールは送らない。

Astroの `dev` / `preview` だけではPages Functionを動かした検証にならない。画面側の入力・事前選択・エラー時の保持と、関数のテストを分けて確認する。

実送信を依頼されている場合のみ、決まった宛先・テスト内容で送信し、画面の成功・Resendの記録・受信箱への到達を確認する。表示確認や解析イベントを作るためだけに、問い合わせを送らない。

障害時は対象環境、変数名、差出人の認証、Resendの配送ログの順で確認する。制限・配送拒否・迷惑メール判定をすべて「キー未設定」と決めつけない。確認できなかった到達は未確認と記録する。

## 2026-09-11のフォーム・受信API

- 共有定義は `src/lib/contact.js`。種類に応じて希望時期、対象・関与範囲、本文の例を切り替える。一般入口の既定は「その他・まだ決まっていない」。`?kind=...&topic=...` は許可された組合せだけを受け入れる。
- テーマ欄は講演なら「講演テーマ」、研修なら「研修内容」と表示する。`contactTopicLabel` を画面・受信メール・メールソフトへの引き継ぎで共用。「その他」は `other-keynote` / `other-training` として選択でき、具体的な希望は既存の必須の相談本文へ記入する。依頼種別を変えたときは、別種別の選択を引き継がない。「まだ決まっていない」と「その他」は区別する。
- 名前・メール・本文の3項目を必須とし、その他は任意。製品・テーマも任意。種類を変えても入力済みの本文は保持する。
- 画面のmaxlengthとサーバー上限を共有する。上限超過は400とfieldを返し、送信しない。サーバーが黙って本文を切り捨てる扱いには戻さない。
- 入力エラーはaria-invalid、aria-describedby、フォーカス移動で示す。入力修正時に解除する。
- 未設定や通信失敗は入力を保持し、ユーザーが押せるメーラーリンクを示す。自動でメールアプリへ切り替えない。メーラー起動を送信完了として扱わない。
- APIからの通知メールにも、依頼種別に合うラベルと、テーマ・製品名を含める。返信メールの自動送信や受付番号の機構は追加していない。
- 通信を模擬する8テストで、再送、未設定、配信失敗、入力不足、最大長、種別・テーマを検証する。実配信の確認は別途必要。
