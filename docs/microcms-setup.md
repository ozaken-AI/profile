# microCMSの設定と表示契約

最終確認：2026-09-07。現在のサービスIDは `ozaken`、APIは `news`（リスト形式）。既存サービスを確認してから変更し、作り直さない。設定画面の名称・契約プランの上限は作業時に確認する。

## スキーマ

正本は [microcms-news-schema.json](microcms-news-schema.json) と `src/lib/microcms.ts`。フィールドIDをそろえる。

| ID | 種類 | 必須 | 表示・用途 |
|---|---|---|---|
| `title` | テキスト | ✓ | 記事タイトル |
| `category` | 単一セレクト | ✓ | 登壇／メディア／イベント／リリース |
| `publishedDate` | 日時 | ✓ | 掲載日、並び順 |
| `excerpt` | テキストエリア | | 記事のリード・メタ説明。現行の一覧には出ない |
| `thumbnail` | 画像 | | 記事の冒頭とOGP。現行の一覧には出ない |
| `body` | リッチエディタ | | 本文。スキーマでは任意だが投稿workflowでは必須 |
| `externalUrl` | テキスト | | 一覧から直接開くURL |
| `eventName` | テキスト | | イベント名 |
| `audience` | テキスト | | 対象者 |
| `scale` | テキスト | | 規模。参加登録者と実参加者を区別する |
| `location` | テキスト | | 場所・オンライン等 |

スキーマのJSONインポート後は、カテゴリの4つの選択肢と複数選択オフを確認し、変更を保存する。選択肢が空のまま取り込まれた過去事例がある。選択肢が出ない場合、記事を重複作成して試す前にAPIスキーマを確認する。

サイトの読み取りはカテゴリの配列・文字列に対応している。ただし投稿スクリプトは配列で送るので、CMSのフィールド型をテキストへ変更する場合は投稿側との整合も検証する。

`publishedDate` は過去の実績を後から追加しても並び順を保つための独自項目。CMSで公開ボタンを押した日時 `publishedAt` と区別する。掲載日・開催日・公開予定を混同しない。

## 実装上の表示

- `getNews()` は掲載日降順で100件ずつ取得し、既定では最大500件。トップは8件を指定する。
- `externalUrl` があれば一覧のリンクは外部へ。**記事の詳細HTMLは引き続き生成される。** 本文が空の場合も、詳細の生成を省く処理はない。
- お知らせの一覧は日付・カテゴリ・タイトルだけ。画像と抜粋を入れても一覧の行には出ない。
- CMS未設定・通信失敗時は空配列に切り替わり、ビルドは成功する。デプロイ成功とは別に実記事の存在を確認する。
- 500件を超える運用に入る前に、取得上限・ページ分割・ビルド時間・サイトマップへの影響を見直す。上限を無制限と説明しない。

## APIキーと設定場所

| 用途 | 設定 | 必要な権限 |
|---|---|---|
| Cloudflare Pagesのビルド | `MICROCMS_SERVICE_DOMAIN=ozaken`、Secret `MICROCMS_API_KEY` | `news` のGET |
| GitHub Actionsの投稿 | Secret `MICROCMS_WRITE_API_KEY` | 新規PUT、既存更新PATCH |
| ローカル開発 | Git対象外の環境設定 | 読み取りが必要ならGET |

読み取りと書き込みのキーは可能な構成では分ける。通常の投稿でPOST・DELETEは使わない。既存のキー権限を変更する場合は利用先を確認する。設定済みの値は会話へ貼り付けず、Secretsの管理経路で登録する。

CloudflareのProduction・PreviewとGitHub Actionsは別々の設定。PreviewでもCMSを表示したい場合は、その環境にも読み取り設定が必要。ローカルにキーがあるだけでは本番へ渡らない。

## CMS更新から自動デプロイする

1. Cloudflare Pagesのプロジェクト `profile` に、対象ブランチ **`claude/ozaken-portfolio-site-a0aggr`** のDeploy hookを用意する。既存のフックと本番ブランチを先に確認する。
2. microCMSの `news` のWebhookにそのURLを登録する。公開・更新・公開終了・削除を反映対象にし、下書き保存の扱いも確認する。
3. フックURLはビルド実行権限を持つ値なので、Git・チャット・公開ログへ載せない。
4. 依頼された実際の公開・訂正の際に、Webhook履歴、Cloudflareの対象ブランチの配信成功、公開サイトの記事を確認する。動作確認のために架空の記事を公開しない。

反映時間を固定で保証しない。投稿成功後もビルドが始まらなければWebhook、ビルド後に記事が欠けたらProductionのCMS設定と取得ログを確認する。

## 日常の編集と旧データ

日常の作成・訂正は [投稿手順](news-post.md)。既存記事の画像や追加フィールドはCMSで編集する。過去記事をまとめて扱う場合は [移行の記録](news-import.md)を読み、既存IDと重複を先に調べる。

スキーマを変えるときはCMSだけを直さず、JSONスキーマ、型、投稿スクリプト、移行ファイルの列、記事表示への影響も確認する。不要そうなフィールドでも、既存データを調べず削除しない。
